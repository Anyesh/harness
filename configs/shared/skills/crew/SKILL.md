# /crew

You are the lead. Asking for a crew is the explicit Herdr request the herdr skill requires. You keep the permission mode the user started you in; if you stop on a permission prompt you look idle and workers' reports wait for you.

While a crew runs, `crew-question-guard.sh` denies your `AskUserQuestion`, `EnterPlanMode` and `ExitPlanMode` and tells you what to do instead. Follow its text; it is the one statement of that exception.

## Start or resume

1. `[[ $HERDR_ENV == 1 ]]` or stop and tell the user to start Claude inside Herdr.
2. Resolve the crew from the shared library, and keep your shell's working directory inside the repo afterwards, because the guard finds the crew from the hook's `cwd`:

   ```bash
   . "$(command -v crew-lib.sh)"
   crew=$(crew_dir) slug=$(crew_slug) main=$(crew_main)
   ```

3. Create `$crew` if needed and make sure `<git common dir>/info/exclude` lists `.claude/crew/`, `.claude/worktrees/` and `.dagr/` (the run file `crew-sweep` writes for the dagr pane, wherever your pane's directory is).
4. No `$crew/lead` file means a fresh crew. Move any `board.tsv`, `rulings.md`, `plan.md`, `reflections.md`, `items/`, `.sweep-seen`, `.sweep-resources`, `.sweep-limits`, `.sweep-leftovers`, `heavy-priority`, `dagr-run`, `dagr-events.jsonl` and `dagr.log` into `$crew/done-$(date +%F-%H%M%S)/`, keeping `brief.md`, `check`, `sweep-check`, `watch-paths`, `thresholds`, `heavy-slots`, `light-slots` and `lead-notes.md`. Item ids continue past the highest id in any `done-*` archive, and never use an id whose `w/<id>` branch or `.claude/worktrees/w-<id>` worktree exists.
5. A `lead` file means resume:
   - If `herdr agent get "$slug-lead"` finds a live agent other than you, rename it to the first free `$slug-old<N>` and leave it open, since it may be a session the user still uses. Until its current sweep returns `SUPERSEDED` it may still edit the board, prompt a worker or close a tab, so after your first sweep re-read the board and check every worker.
   - A `lead succession <name> <profile>` line in `rulings.md` naming you (your herdr name before step 6) means an old lead at its usage limit started you. It acts on nothing from then on, so skip the re-read above. Ask the user nothing before step 6, because until then your role is `none` and the question guard does not stop you.
   - A reboot or reset can rename the host, drop profiles and empty temp dirs, so re-derive both from the live host. Read the pool again from `claude-profile names` and log in `rulings.md` each worker whose profile is gone, so you replace it. Then run `crew-missing-paths`, which checks every absolute path named in the files at the top of `$crew` (`check`, `sweep-check`, helper scripts kept beside them, `brief.md`, `lead-notes.md`) and in item specs, and fix or recreate each `missing:` path it prints before you assign work.
   - Run `crew-merge --status`, and `crew-merge --settle <id>` for each `CUT` or `STALE` line it prints. Then mark `done` every item with a `merged` file and every report-only item whose report is `done`, and re-read reports you have not acted on.
6. Name yourself `$slug-lead` with `herdr agent rename` and write `$crew/lead` as your pane id and session id separated by a tab: `$HERDR_PANE_ID` and the `.agent_session.value` of your pane in `herdr pane list`. Do this before you spawn a worker or start a sweep, because without it every sweep prints `SUPERSEDED`. After `/clear` your session id changes and your sweep prints `SUPERSEDED`, so run `/crew` again to resume. Never restart a sweep that printed `SUPERSEDED`; if you think it is wrong, run `crew-role` and act on its answer.
7. Read `lead-notes.md` and the `## Lessons` lines in `brief.md`. Act on a `## Handover` heading in `lead-notes.md`, which a lead at its usage limit left, then delete it. If a `lead succession` line names you, that lead started you on purpose: log `lead succession taken <name>` with the name that line gives, and tell the user its tab (now `$slug-old<N>`) can be closed. Finish or close any spawn that `rulings.md` shows as started but never assigned. On a fresh start, append the first dated line to `reflections.md`, so the first sweep does not ask for a reflection.
8. If the user handed you a plan, split it into board items with `references/intake.md` now, after any archive in step 4.

## Files you own

- `board.tsv`: tab-separated `id status owner branch into updated deliverable deps`, no header, `status` one of `open|assigned|done|blocked`, `updated` in epoch seconds, `owner` the worker's agent name, `branch` `w/<id>` and the optional `deps` the comma-separated ids of items that must be `done` first. Only you edit it, and only through `crew-board`: `add <id> <into> <deliverable> [deps]` writes an open row, `set <id> field=value...` changes `status`, `owner`, `into`, `deliverable`, `deps` or `updated` (stamped now unless given), and `show` prints it. Give each `crew-board` call its own Bash call, because zsh drops a whole command line on a parse error and an edit bundled with other commands can silently not happen.
- `rulings.md`: timestamped decisions, the done bar, and every worker number used with its profile.
- `brief.md`: what workers in this repo need beyond `references/worker.md`, such as test commands, build paths that must not depend on the checkout location and what not to touch, with the lessons from reflection under `## Lessons`. Give each worktree its own build output dir and the merge gate one more, never shared and built with smaller debug info, and run tests that could reach a live service through an isolation wrapper (`references/isolation.md`).
- `check`: an executable gate that `crew-merge` runs in a temporary merge of the item into its target. Write it before the first assignment.
- `sweep-check`: an optional executable that `crew-sweep` runs in the main checkout after each wait, for checks that should run while work is under way (stray logs, a service that should be down). It prints its findings and exits 0; a non-zero exit means the check itself broke. It only reads: it never changes tracked files, the index or refs, because `crew-merge` needs the main checkout clean and fast-forwards it.
- `watch-paths`: optional, one absolute path per line (build output dirs, caches) whose disk `crew-resources` checks besides the main checkout and the runs dir; a path that does not exist yet is checked at its nearest existing parent.
- `thresholds`: optional `KEY=value` lines, read by `crew-resources` and `crew-sweep` on every sweep so a resumed lead keeps them; a non-empty environment variable overrides a line. Keys: `CREW_DISK_MIN_GB`, `CREW_MEM_MIN_MB`, `CREW_LOAD_PER_CPU`, `CREW_IO_FULL_PCT`, and the whole-number keys `CREW_SESSION_SOFT_PCT` (70) and `CREW_WEEK_SOFT_PCT` (85), above which a profile takes no new work, `CREW_SESSION_HARD_PCT` (90) and `CREW_WEEK_HARD_PCT` (95), at which its workers hand off, `CREW_CONTEXT_K` (400, thousands of tokens of context before a worker hands off), `CREW_OPENCODE_CONTEXT_K` (300, the same for opencode workers) and `CREW_WORKERS_PER_PROFILE` (5).
- `heavy-slots`: optional, containing `1`; it turns on the heavy slot below.
- `heavy-priority`: optional, one item id per line, whose heavy-slot waiters are served with the merge gates (Heavy slot).
- `light-slots`: optional, a whole number of at least 1; it turns on `crew-light` (Heavy slot).
- `items/<id>/report-only`: an empty marker intake writes for an item whose deliverable is a check or a report, which lands nothing and has no `merged` file.
- `plan.md` and `items/<id>/spec.md`: the plan you were handed and each item's part of it (`references/intake.md`).
- `items/<id>/build-dir`: when the repo gives items their own build output dirs, the item's resolved absolute dir (no template), whose last component is the id or `w-<id>`. `crew-clean-build <id>` deletes that dir when the item lands.
- `lead-notes.md`: rules for you from reflection, and `## Proposed /crew changes` for every crew in any repo.
- `reflections.md`: one dated line per reflection round (`references/reflect.md`).
- `dagr-events.jsonl`: append-only, one dagr event object per line, which `crew-dagr` publishes as the run file's `events[]` because it rewrites that file every sweep. When you resolve a `[DAGR OPERATOR MESSAGE]`, append `{"at":"<date -u +%FT%TZ>","type":"message_resolved","task":"<id>","message_id":"<its message_id>","actor":"$slug-lead","detail":"<what you did>"}` here, never to the run file; a line `dagr check` would reject or whose task is not on the board is dropped and logged in `dagr.log`.

## Heavy slot

On a machine that cannot run a Docker stack, a browser check and the merge gate at once, write `1` to `$crew/heavy-slots` before the first assignment. `crew-heavy` then keeps one machine-wide slot: workers hold it for Docker stacks and anything run against them, dev servers, browser checks and whole-suite runs, and `crew-merge` holds it as `merge-<id>` while `check` runs, waiting up to three hours for it (`CREW_HEAVY_MERGE_WAIT` in seconds). Use `crew-heavy status` to see who holds it, and never run `acquire` from your own shell to test it, because you would queue behind the workers and then take the slot from the real queue. Each waiter holds a ticket in `$crew/heavy.queue` while it waits, a dead waiter's ticket is dropped, and `status` lists live waiters in serving order on a `waiting:` line. Merge gates, the item ids in `heavy-priority` and tickets older than `CREW_HEAVY_AGE` seconds (default 3600; keep it below `acquire`'s max wait) are served first, oldest first, then everyone else in arrival order, and a normal waiter also stays behind a merge that is queued for or holds the merge lock but has no heavy ticket yet. Priority is re-read on every poll, so adding an id reaches a worker already queued and removing it demotes it. Grant priority only to the last items on the critical path, because until its ticket ages a normal waiter yields to every merge and grant that arrives. A normal waiter that checked the queue just before a merge wrote its marker can still take the slot, so that merge waits one session. Never edit `heavy.queue` by hand.

Frontend-only items can share one prebuilt review stack on the target branch while each holds the slot, started by a repo script that refuses to start unless `crew-heavy holds <id>` exits 0. There is one stack per machine, so backend, migration and seed items build their own. A rebuild wipes seeded data, and a worker stops its dev server before it releases the slot. colima's forwarder can stop forwarding newly published ports, and `ssh -L` cannot bind 80 or 443 as a non-root user, so forward high ports only.

With a whole number N in `$crew/light-slots`, workers run type checks, lint and unit tests through `crew-light <command...>`, which runs at most N at once and starts none while a live merge gate holds the heavy slot; commands already running go on, and `check` runs with `CREW_MERGE_GATE=1`, so it never waits on its own gate. The pause needs `heavy-slots`, because without it `crew-merge` takes no heavy slot.

## Workers

The pool is `claude-profile names` plus `default`, your own `${CLAUDE_PROFILE:-default}` included. A profile runs at most `CREW_WORKERS_PER_PROFILE` live Claude sessions, counting every crew's workers and leads and the user's own sessions on it, since they share its usage limit. Spread workers over every profile in the pool that is below both soft thresholds and under `CREW_WORKERS_PER_PROFILE`, yours included, preferring the one with the most headroom: the lowest session figure, then the lowest week figure, from the sweep's `POOL` lines. Your profile counts you as one session, so the cap already leaves room for you. When your profile nears its usage limit, close or replace the workers on it first, since losing you stalls the crew.

Your status line and Claude's usage warnings never reach your context; the sweep's `POOL` lines carry every profile's figures instead, yours included.

opencode is optional. While the sweep prints a `POOL opencode` line (opencode is installed on this machine with an Anthropic key), opencode is in the pool, listed last, and you spawn on it only when every Claude `POOL` line is `FULL`. Its workers run on the paid API key, so their cost grows with their context and with every cold cache. Every opencode rule here and in `references/worker.md` applies only to opencode workers, so a crew on a machine without opencode runs on Claude profiles alone.

To spawn one worker:

1. N is one past the highest worker number in `rulings.md` or any `done-*/rulings.md`, below 1000. Write it to `rulings.md` with the profile before anything else, and if `herdr agent get "$slug-wN"` finds an agent, take the next N.
2. Run `crew-spawn "$slug-wN" "$profile"` with a 600000 ms Bash timeout, because its prompt poll and up to three `agent start` tries can take up to its 540 s deadline. It creates the tab labelled `$slug-wN` with `HARNESS_UNATTENDED=1`, `HARNESS_NOTIFY=0`, the profile's env and an empty and a dead push URL for each remote. The empty value resets each remote's push URLs, so `git push` to a named remote fails while fetch still works; nothing but the worker's instructions stops `git push <url>`, a publish or a deploy. It then waits for the shell's prompt and starts Claude with `--dangerously-skip-permissions`, retrying only while the shell is at its prompt and stopping once Claude runs in the foreground, which it recognises by argv0, since herdr reports the native install's process name as its version number. For opencode, run `crew-spawn "$slug-wN" opencode`: it first checks that `opencode models anthropic` lists the worker model (`CREW_OPENCODE_MODEL`, default `anthropic/claude-opus-5-5`) and exits 4 creating nothing when it does not, skips the profile env, passes `OPENCODE_CONFIG_CONTENT` (every tool allowed, the question tool off, and a `crew-review` subagent on `CREW_OPENCODE_REVIEW_MODEL`, default `anthropic/claude-fable-5-1`), and starts opencode on that model.
3. A `pane <id>` line on its output means the tab was created, and it exits with the last `agent start` status. It prints `exists <name>` and exits 3, creating nothing, when an agent or a tab already has that name: for a tab left by an earlier killed run, close that tab by label under the closing rule below and spawn under a new N. Any other failure prints `crew-spawn: <message>` and exits 4.
4. On `agent_not_ready`, read the screen with `herdr agent read "$slug-wN" --source visible --lines 40`:

   - The workspace trust dialog ("Is this a project you created or one you trust?", with `❯ No, exit` above `Yes, I trust this folder`) gets `herdr agent send-keys "$slug-wN" Down Enter`, because running `/crew` here is the user's trust decision; then wait for `idle`.
   - A startup step within authority the user already gave, such as approving the repo's `.mcp.json` servers, gets answered with `send-keys`.
   - Anything else, such as a login or billing prompt, means you close the tab and tell the user.
   - An opencode worker has no trust dialog, so read its screen, close the tab and tell the user.

   If `herdr agent list` then shows the pane with an empty `.name // ""`, rename it.

5. Only now run `crew-board set <id> status=assigned owner=$slug-wN`, which also sets `updated` to now. If the repo gives items their own build output dirs, write the item's dir to `items/<id>/build-dir`.
6. Brief it in one prompt starting with `[crew] `, the prefix cache-guard lets through a cold cache. Name `references/worker.md` in this skill, `$crew/brief.md`, the item id, its deliverable, its `$crew/items/<id>/spec.md` if intake wrote one, its `$crew/items/<id>/build-dir` if you wrote one, its stop point (by default landed for an item from a plan, otherwise the mechanism and a red test, before any fix), the target branch, and for a replacement the existing worktree it takes over. For a new item write "create your worktree at `$main/.claude/worktrees/w-<id>`", because "your worktree is <path>" reads as an existing one, which `references/worker.md` has the worker report as blocked. For an opencode worker, name `references/worker.md` by its absolute path, `$HOME/.agents/skills/crew/references/worker.md` expanded, and tell it to apply its `## In opencode` section. Say that the user asked for workflows only when they did.

Address workers only by name: `send-keys` and `agent prompt` take the name. To close a worker's tab, take the `tab_id` of the `herdr tab list` entry labelled `$slug-wN` at that moment, and close nothing unless exactly one tab carries that label, noting it in `rulings.md` instead.

## Loop

Run `crew-sweep` as the whole command of a `run_in_background` call, with no `&`, `disown` or output redirect, since each detaches it from the task notification that wakes you. It waits up to 900 seconds for an item file to change, or takes the wait in seconds as its argument. Act on everything it prints in the same turn, then start it again. Each worker with an `assigned` row gets a line `WORKER <name> item <id> <herdr status> on <profile>` (`on ?` until its status line first reports, `on opencode` for an opencode worker) followed by any of the flags below.

- `SUPERSEDED`: another session is lead now, so stop acting as lead.
- `ALL-DONE`: assign the next open work if there is any, otherwise close out.
- `ERROR <step>: <message>`: a crew-role or herdr call failed and the sweep retried it; if the sweep exited after repeated errors, tell the user what failed and start it again.
- `CHANGED <path>` or `REMOVED <path>`: read that file. `TIMEOUT` means nothing changed during the wait.
- A changed `report.md`: answer a `question` with a `[crew]` prompt and run `crew-board set <id>`, which sets `updated` to now, so the sweep watches that worker again; for `done` with a `merged` file, or `done` on a report-only item, which has none, mark the row `done`, assign in the same turn what it unblocks, and give the worker its next item or close its tab. For a `done` report that names a leftover build dir, rerun `crew-clean-build <id>` from the repo; a refusal of the path itself (its last component, or a protected dir it is, holds or sits in) repeats, so then correct `items/<id>/build-dir` and rerun it, or delete the dir yourself under the `RESOURCE` rule below (nothing `RUNNING` or `QUEUED`, no worker building there). For `blocked`, mark the row `blocked` and log the reason, except when the item has a `merged` file whose tip is in `into`: it landed and only cleanup failed, so mark it `done`, log the error and let `LEFTOVER` clean up. Handle `rate-limited` as a usage limit under `IDLE`, and `handoff` under `LIMIT` or `CONTEXT`, whichever prompted it.
- `READY <id>`: an open item whose deps are all `done`. Assign every READY item before you start the sweep again, unless a disk, memory, load or io `RESOURCE` breach is active: give it to a `SPARE` worker without `holds` or `CONTEXT` on a profile below both soft thresholds, otherwise spawn one on a profile without `FULL` (opencode only when every Claude `POOL` line is `FULL`), in both cases preferring the profile with the most headroom (Workers), and on a tie or a `?` figure, the one whose figures are known. Count each worker you spawn or give work this turn toward its profile, which is full once that count reaches the cap. A worker's split proposal becomes new board items with deps, assigned the same way, and the original item's deliverable (`crew-board set <id> deliverable=...`) and `spec.md` narrow to the part its worker keeps.
- `POOL <profile> <crew>/<all>/<cap> session <x>% week <y>%`: this crew's live workers, every live Claude session on the profile, the cap, and its usage (`?%` when no session has reported a figure for the current window). ` FULL` means it is at the cap or a soft threshold and takes no new worker.
- `POOL opencode <crew>/<all>/<cap> api`: the same counts for opencode, which has no usage window, so ` FULL` means only the cap. It is printed only while opencode can run a worker here (Workers).
- `on opencode` (on `WORKER` and `SPARE` lines): an opencode worker, which pays for every token and loses its prompt cache after 5 idle minutes. Answer its `question` or `handoff` report before Claude workers', hand it off at `CONTEXT` unless it is one step from landing, and close its tab when its item is done rather than leave it `SPARE`. While it blocks in a long foreground wait (the heavy slot or a merge, expected past about 90 minutes), your prompt reaches it only when the wait ends, so a hand-off can lag by that long.
- `LIMIT <profile> <session|week> <x>% resets in <m> min`: a profile with your workers, or your own, reached a hard threshold. It wakes you once per window and repeats on every sweep (`WOKE`). If the reset is under 20 minutes away, let the workers run (the `IDLE` rate-limit wait covers them). Otherwise, when a target exists (a `SPARE` worker without `holds` or `CONTEXT` on a profile below both soft thresholds, or room on such a profile, preferring the profile with the most headroom (Workers); a `?` profile counts, after those with known figures), prompt each worker on it that is not `MERGING` with `[crew] hand off now`, moving your own profile's workers first. On its `handoff` report, close its tab and give the item, its worktree and `items/<id>/handoff.md` to the target. With no target, let the workers run into the limit and tell the user when it is the week window. On a repeat, recheck the `POOL` lines for a target whenever workers remain on the limited profile, because profiles can appear mid-crew and a worker moved at the hard threshold can still write its hand-off while one at 100% cannot. When your own profile is at a hard threshold with its reset 20 minutes or more away, hand over to a successor lead as below, rechecking for a target on each repeat; with no target, write the crew's state under a dated `## Handover` heading in `lead-notes.md` and tell the user to resume `/crew` from another profile.
  - Target: another profile below both soft thresholds with room under `CREW_WORKERS_PER_PROFILE`, where the successor counts as one session, chosen by the most-headroom rule (Workers). Never opencode, since the lead runs `/crew`, which needs Claude Code. Never start a second successor while a `lead succession` line naming a successor other than you has no `taken` or `failed` line after it.
  - Name: `$slug-l<N>`, with N the first number no `lead succession` line in `rulings.md` or any `done-*/rulings.md` names, because herdr renames the agent but not its tab, so a reused name would hit `crew-spawn`'s tab check. When `crew-spawn` still exits 3 (a tab left by an earlier crew), log the name in `rulings.md` and take the next N.
  - Steps: write the crew's state under a dated `## Handover` heading in `lead-notes.md`, log `lead succession <name> <profile>` in `rulings.md`, and run `crew-spawn --lead <name> <profile>` as spawn step 2 says. `--lead` leaves out `HARNESS_UNATTENDED` and `HARNESS_NOTIFY`, under which `crew-role` would answer `worker` and the successor could never lead, and keeps the push-URL guard. Handle `agent_not_ready` and the trust dialog in its pane as spawn step 4 does, then send that agent the prompt `/crew` with no `[crew]` prefix: a fresh session has no cache for cache-guard to protect, and a prefixed prompt would not run the command. The successor runs with Claude's skip-permissions flag like every crew session, whatever mode the user started you in. Its resume renames you to `$slug-old<N>`, takes `$slug-lead`, writes `$crew/lead` and acts on the Handover.
  - No gap: from the `/crew` prompt on, act on nothing (no sweep, no answers, no Handover appends), ignore output from a sweep that was already running, and run only `crew-succession-wait <name>` with `run_in_background`. Questions wait a few minutes for the successor, whose resume re-reads unanswered reports.
  - `TAKEN <pane>`: the successor leads. Stop acting as lead for good and write nothing under `$crew` or to `lead-notes.md`, so no late write recreates a Handover the successor deleted.
  - `ORPHANED <pane>`: the successor took over, then died. Tell the user to resume `/crew`, since nothing else will.
  - `FAILED gone` or `FAILED no-agent`: the successor has no tab or no live agent. Close its tab if present, then write `$crew/lead` with your own pane and session even if it already names you, retry `herdr agent rename` back to `$slug-lead` until herdr frees the name, log `lead succession failed <name>` in `rulings.md`, tell the user to resume `/crew` from another profile, and lead on.
  - `WAITING`: no outcome within its wait (default 600 s). Read the successor's screen: a login or billing prompt counts as `FAILED`; anything else, run `crew-succession-wait` again.
  - `ERROR <step>`: a herdr call kept failing, or `$crew/lead` is missing or unreadable (`ERROR lead-file`). Tell the user what failed and run it again.
- `WOKE limit <profile> <window>` or `WOKE context <name>`: that `LIMIT` or `CONTEXT` alert is new on this sweep. Both state lines repeat on every sweep, so log each `[crew] hand off now` prompt as a dated `handoff asked <name>` line in `rulings.md` and each worker you move off a profile for a `LIMIT` as `limit moved <name> <profile>`, which tell you after your own compaction what you already did. A `LIMIT` or `CONTEXT` with a matching `WOKE` line is new: act on it as its rule says. One without was alerted earlier: read those `rulings.md` lines and the item's report, and finish only the steps still undone; prompt `hand off now` only when the worker is not `MERGING`, has no `handoff` report and has no `handoff asked` line from the last `CREW_QUIET` seconds (an hour by default). A `WOKE` with no matching state line means the sweep lost that line, so the next sweep's `CONTEXT` or `LIMIT` for it counts as new.
- `CONTEXT <n>k` (a flag on `WORKER` and `SPARE` lines): the session holds at least `CREW_CONTEXT_K` thousand tokens (`CREW_OPENCODE_CONTEXT_K` on opencode), or 80% of its window. It wakes you once per session and repeats on every sweep (`WOKE`). Prompt the worker `[crew] hand off now` (not while `MERGING`), close its tab on the `handoff` report, and brief a fresh worker on the same profile with the worktree and `handoff.md`, unless that profile is at a hard threshold, which makes it a `LIMIT` handoff.
- `SPARE <name> <status> on <profile>`: a live worker with no `assigned` row, ` holds <id>` when it owns a `blocked` one. Give it a READY item when its profile is below both soft thresholds and it has no `CONTEXT`, otherwise close its tab; one that `holds` an item blocked on the user keeps its tab until the answer comes. `SPARE <label> no agent`: a worker tab whose Claude exited; close it. A `SPARE` line can be older than your latest spawn or assignment, so right before acting on one, check with `crew-board show` that the name still owns no `assigned` row and, for `no agent`, that `herdr agent get <label>` still finds none; leave alone only a worker you are spawning in this same turn.
- `LEFTOVER <id> <worktree|branch|build-dir> <path or ref>`: a landed item whose worktree, `w/<id>` branch or build dir is still there. From the main checkout run `git -C "$main" worktree remove <path>`, `git -C "$main" update-ref -d refs/heads/w/<id> <tip from items/<id>/merged>` and `crew-clean-build <id>`, and log any refusal in `rulings.md`; each leftover is printed once. A report-only item has no `merged` file, so delete its branch only when `git -C "$main" rev-list --count <into>..w/<id>` prints 0, with `update-ref -d` on the branch's current tip.
- `DEPS <id> <problem>`: an open item that can never start, because a dep `names unknown` id, it `waits on blocked` item, `is in a cycle` or `waits on stuck` item. Fix the order on the board or mark the row `blocked`, logging in `rulings.md` which dep blocked it; for `waits on stuck`, fix the stuck dep's own DEPS line instead. When a dep you logged as a cause can finish again (reopened, added to the board or its order fixed), reopen the rows you blocked because of it.
- `GONE <name>`: its Claude exited or its pane closed (herdr drops a name 10 to 15 seconds after exit). Close its tab by label, then give the item to a fresh worker that takes over the same worktree.
- `IDLE`: read its screen. "Usage limit reached" means it is rate-limited and cannot write its own report. When the reset it shows is under 20 minutes away, keep the worker: run the next sweep with the seconds left until the reset as its wait, then prompt the worker with `[crew]` to continue. Otherwise replace it on another profile; for an `IDLE HEAVY-HOLD` worker do so at once and leave its slot held, because the hold is keyed on the item id and the replacement, which takes over the same item, owns it. Add to that brief: "the heavy slot is held under your item id; stop any stack or dev server the previous worker left running, then release the slot or keep it if you need it now", since releasing first would let a merge gate run `check` beside the old stack. Any other idle screen: prompt it or replace it. `HEAVY-WAIT` and `LIGHT-WAIT` hide `IDLE`, so a waiter that hits its usage limit shows only once it holds the slot, as `IDLE HEAVY-HOLD`.
- `HEAVY-WAIT <m>m`: the item id, or its `merge-<id>`, has a ticket in the heavy queue, `<m>` minutes old. Leave it waiting; to serve it sooner, add its id to `heavy-priority`.
- `LIGHT-WAIT`: a `crew-light` command of the item waits for a light slot or for a merge gate to finish. Leave it waiting.
- `HEAVY-HOLD`: the item id, or the `merge-<id>` of its running merge, holds the heavy slot. An item-id holder gets `QUIET` only after `CREW_HEAVY_LONG` seconds (default 5400) with no progress, counted from the later of its last progress and the hold's start. `IDLE HEAVY-HOLD`: read the screen; a background stack or browser run in progress is fine.
- `QUIET`: the item shows no progress (row update, report, notes, merging file or commit on its branch) for an hour. Read the worker's screen and `items/<id>/notes.md`, then prompt it, split the item or replace the worker. A note counts as progress for only an hour, so when the last `notes.md` line names a long run still inside its expected length and the screen shows it running, leave the worker alone. A worker with an unanswered `question`, `blocked` or `handoff` report is never QUIET.
- `DIALOG`: read the screen it shows, then answer with `send-keys` within the same limits as at spawn or replace the worker, and log the call in `rulings.md`.
- `HEAVY <holder> <minutes> min <purpose>`: the heavy slot has been held for over 90 minutes while someone waits for it, a heavy-queue waiter or a `crew-light` waiter behind a running merge gate. Read the holder's screen (a `merge-<id>` holder is that item's worker merging); prompt a worker that holds it while idle to release it, and run `crew-heavy release <holder>` yourself only when the item has no live worker and you are not replacing its worker. `HEAVY failed: <message>` means `heavy-slots` holds something other than `1`, which also stops every merge, so fix the file.
- `STALE-MERGE <id>`: a `crew-merge` run died (a kill, crash or reboot) and left its marker. Run `crew-merge --settle <id>`, then `crew-heavy release merge-<id>` if it still holds the heavy slot. If it reports the item landed, the item now has a `merged` file, so mark it `done`; otherwise prompt its worker, if it is live, to rerun `crew-merge`.
- `MERGING`: the worker's `crew-merge` is running or queued for the merge lock. Leave it alone, and never close or replace a worker while it merges. `MERGING QUIET` means its merge has run for an hour, not counting time spent waiting for the heavy slot, possibly a hung `check` holding the merge lock for every item: read `check-<id>.log` in `${CREW_RUNS_DIR:-$HOME/.cache/crew-runs}/$slug` and tell the user, without closing the worker.
- `RESOURCE <line>`: `crew-resources` found low free disk (`disk <mount> <N> GB free (<path>)`, under `CREW_DISK_MIN_GB`, default 20, and `critical` under a quarter of that), low memory (`memory`, under `CREW_MEM_MIN_MB`, default 1024), a 5-minute `load` above `CREW_LOAD_PER_CPU` (default 2) per CPU, or I/O stalls (`io <x>% full over 60 s (D state: <names>)`, Linux only, above `CREW_IO_FULL_PCT`, default 30), where tasks wait on disk while the CPU idles: pause builds rather than add workers. Set lasting thresholds in `$crew/thresholds`. A new breach ends the sweep's wait, and one that lasts wakes you again every 10 minutes. In the same turn free space, or tell workers with a `[crew]` prompt to stop building until you say. Before you delete a build or runs dir, `crew-merge --status` must list nothing `RUNNING` or `QUEUED` and no worker may be building there, since deleting it under a merge gate or a build breaks that run. `RESOURCE failed: <message>` means a probe itself broke, such as a hung mount named in `watch-paths`; fix it.
- `REFLECT`: run a reflection round with `references/reflect.md`. It may arrive up to one wait late.
- `CHECK <line>`: output from `sweep-check`; act on what it flags. `CHECK failed: <message>` means the check itself failed or timed out after 30 seconds, so fix it.

When you replace a worker, close its tab first, then spawn the new one and brief it with the worktree it takes over.

## Your rules

- Decide product, scope and performance calls yourself and log each in `rulings.md`. Ask the user only for authority, in plain text at the end of a turn, and keep the other items moving meanwhile.
- Read reports and capped tails only. Never write feature code, run builds or suites, push or deploy, because your profile hits its weekly cap first.
- Each item has one owner, assigned only by you; workers never hand each other work.

If that call fails because the profile has no Fable, pass `model: "opus"` and stay on Opus for the rest of the session. Subagents for broad reading or log scanning keep the cheaper model the global rules name.

## Stop

When the user says to stop the crew, close every worker tab (waiting for any `MERGING` worker to finish first), list each open item's branch and worktree for the user, and delete `$crew/lead`. A later `/crew` starts fresh.

## Close-out

1. Close every `$slug-w<N>` tab, then run a last reflection round with `references/reflect.md`, saving user preferences and cross-crew gotchas to project memory as it says, then delete `$crew/lead`, which also ends the question guard for you.
2. For every `w/<id>` whose tip is already in its target, run `git -C "$main" worktree remove <path>` and then `git -C "$main" branch -d w/<id>`, never with `--force`, then `crew-clean-build <id>`, and list any that refuse.
3. Write one devlog entry for the crew's outcomes.
4. Tell the user the list under `## Proposed /crew changes` in `lead-notes.md`, then remove the entries you told, so the next crew does not repeat them.
5. For each `blocked` item, tell the user the branch it is left on if that branch still exists, and `.git/worktree-salvage/` if the SessionStart worktree sweep salvaged its worktree. That sweep may remove a worktree after a day idle but keeps unlanded branches.
