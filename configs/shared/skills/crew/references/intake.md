# Plan intake

Read when the user hands the crew a plan. Run it after Start step 7, so a fresh crew has already archived the previous crew's files and written its first reflection line.

1. Copy the plan to `$crew/plan.md`.
2. Split it into items. Each item lands as one reviewed merge, fits one worker session and has a deliverable someone can observe (a test that passes, a command that prints X). Pieces that would edit the same files become one item, or a chain through `deps` so they never run at once.
3. Decide the plan's open choices yourself and log each in `rulings.md`; the question guard denies you `AskUserQuestion` while the crew runs.
4. Have the split reviewed by a fresh subagent, on the judgment-subagent model under `SKILL.md`'s Your rules, that only reads and never runs the product's binaries, installed or built: give it `plan.md`, the proposed items with their deliverables, deps and spec text, and the repo, and ask whether every part of the plan is in some item, whether each item can land on its own, which items would edit the same files without a dep between them, and whether the order holds. Run the rounds as the global plan-review rule sets them: the reviewer answers APPROVE, optionally with notes, or CHANGES NEEDED only for a blocker, with its evidence; you apply notes without a new round and check each blocker against the code yourself before changing the split; a blocker that repeats a mechanism you already patched means a new design for that part. If the third round still finds a blocker, stop the intake and tell the user which part of the split keeps drawing findings, and whether the split patches findings instead of fixing its design or the reviewers were given the wrong context.
5. Write each item's part of the plan to `$crew/items/<id>/spec.md`: its design decisions, exceptions and edge cases, plus every constraint the plan sets for all of its work. The board's deliverable is a one-line label; the spec is what the worker builds and is reviewed against. An item with an open-ended domain (input formats, edge cases) gets its done bar in the spec as an enumerated list, and anything outside that list becomes a follow-up item, so the worker can finish.
6. Add the board rows with `crew-board add`, one Bash call per row, all `open`, with `deps` naming only ids on the board and forming no cycle; ids follow Start step 4. An item's stop point is landed (merged) unless the plan says otherwise. An item whose deliverable is a check or a report (an end-to-end pass that lands nothing) gets an empty `$crew/items/<id>/report-only` file, with its stop point "reported".
7. Write `check` if it does not exist, run `crew-sweep 0` (one comparison, no wait), and act on everything it prints as the Loop says, assigning `READY` items while a profile has room (the Loop's `READY` rule). Then start the Loop.
