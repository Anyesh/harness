# Reflection round

Read when a sweep prints `REFLECT` and at close-out. A round turns what went wrong since the last one into rules where they are enforced, so the same mistake costs time once.

1. Read what changed since the last round: reports and their `lessons:` sections, each item's `notes.md` (where workers log non-green reviews and failed merge gates), workers you replaced, `CHECK` lines, new rulings, and how many items opened and closed.
2. For each lesson, name the class of mistake rather than the one instance, then put it where it is enforced, in the same turn:
   - A rule for workers goes into `$mem/brief.md` under `## Lessons` through `crew-lesson add "<rule>"`, one imperative line stating the class, never an item id, a measured value or one situation. Each write cleans as it goes: run `crew-lesson similar "<rule>"` first and, when a line of the same class exists, rewrite that line to cover both (Edit, not a second line), and delete any line the new rule makes stale. `crew-lesson add` refuses a near-repeat and any line past the section's size limit (`CREW_LESSONS_MAX_BYTES`, 8 KB by default); then merge or retire lines until it fits, never raise the limit to make room.
   - A class that fails again after its lesson was written needs a mechanism, not more text: open a board item that builds the check into the script or tool where the mistake happens, and delete the lesson line once that item lands. Send the new lines in one `[crew]` prompt, saying it is not an answer, to every live worker not flagged `DIALOG`, `MERGING`, `IDLE` or `GONE`; those catch up when they re-read the lessons before landing. A worker whose current report is an unanswered `question` gets the lines with its answer instead.
   - Anything a script can catch goes into `sweep-check` (while work runs, read-only), `check` (at merge) or a new `preflight.d/` entry (every item, before the batch). Each `ESCAPE <id>` line gets a `preflight.d/` check that would have refused that item, then delete `$crew/items/<id>/gate-escape`.
   - A rule for you goes into `$mem/lead-notes.md` through `crew-lesson add --lead "<rule>"`, which appends it at the end; move the line under the topic heading it belongs to.
   - A rule every crew in any repo should follow goes into the harness wiki folder's `proposed.md` through `crew-lesson add --all "<rule>"`, worded for any repo; a harness session promotes it (`references/promote.md`).
   - A preference of the user's, or a gotcha a later crew in this repo would hit again, goes to Claude Code's project memory when your session has a memory directory: one fact per file, with a line for it in that directory's `MEMORY.md`. Repo files alone do not carry what a crew learns about the user past the crew.
3. Read `crew-lesson size`; the limit keeps the brief short, so a round that adds lessons also retires the ones a landed mechanism or a later change made stale.
4. Change `check`, `preflight`, a `preflight.d/` entry or `sweep-check` only by writing `$mem/.tmp-<name>`, running `chmod +x` on it and moving it over the old one with `mv`. Bash reads a running script as it goes, wiki-sync skips dot paths so a half-written one is never synced, and `crew-merge` refuses a `check` that is not executable.
5. Look at throughput: items replaced twice, items stuck since the last round, profiles with room and no worker. Act on each.
6. Append one dated line to `reflections.md` saying what the round changed, even when nothing was learned; it resets the sweep's `REFLECT`.
